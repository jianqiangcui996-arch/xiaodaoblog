<hr>
<h2 id="一、缘起：我想在手机里养一个本地大模型">一、缘起：我想在手机里养一个本地大模型</h2><p>最近在折腾端侧大模型推理，目标很明确：</p>
<blockquote>
<p>把 <strong>Spark-X2.5-4B-Q4_K_M.gguf</strong>（讯飞星火 X2.5-4B 的 4-bit 量化版）塞进安卓手机，用 <strong>PocketPal AI</strong> 这个开源 RN 应用离线跑起来，不依赖任何云端。</p>
</blockquote>
<p>PocketPal 本身是微软出品、基于 React Native 的本地模型客户端，底层用 <code>llama.rn</code> 绑定 <code>llama.cpp</code>。理论上只要把最新的 <code>llama.cpp</code> 里已经合入的 <code>spark2_5</code> 架构支持接上，再打出 APK 就行。</p>
<p>听起来像是「git clone → 改两行 → 构建」的下午茶项目。</p>
<p>事实证明，我太天真了。</p>
<hr>
<h2 id="二、接手时的一地鸡毛">二、接手时的一地鸡毛</h2><p>前一位同学（用 VS Code 跑了一阵）留了一份交接文档，结论是：</p>
<blockquote>
<p>「<code>spark2_5</code> 代码补丁已经补齐，但 Android 打包链路在当前 Windows 环境里没跑通，建议从 <code>.env</code> + Gradle 任务 + 输出路径 + 变体过滤继续排查。」</p>
</blockquote>

<hr>
<h2 id="三、核心认知：为什么补丁打了却没用">三、核心认知：为什么补丁打了却没用</h2><p><code>llama.rn</code> 默认走<strong>预编译好的 <code>.so</code> 库</strong>（<code>RNLLAMA_BUILD_FROM_SOURCE=OFF</code>），而且仓库里压根没带这个预编译库。即便你给它把 <code>spark2_5.cpp</code> 的补丁打进了 <code>node_modules/llama.rn/cpp/models/</code>，只要它不重新从源码编译，那补丁就是个摆设。</p>
<p>正确姿势是强制源码编译：</p>
<figure class="highlight powershell"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br></pre></td><td class="code"><pre><span class="line">gradle.bat assembleProdDebug `</span><br><span class="line">  <span class="literal">-PrnllamaBuildFromSource</span>=true `</span><br><span class="line">  <span class="literal">-PrnllamaVariants</span>=rnllama</span><br></pre></td></tr></table></figure>

<p>好消息是 <code>rnllama</code> 的 CMake 用 <code>file(GLOB models/*.cpp)</code> 自动扫模型实现目录，<code>spark2-5.cpp</code> 会被自动编进去；再配合 <code>-PrnllamaVariants=rnllama</code> 只编 generic 变体，避免把一堆用不上的架构都拉来编译。</p>
<blockquote>
<p>这一条值得所有人记住：<strong>改了 llama.cpp 的模型源码，就必须从源码编，预编译 <code>.so</code> 不会自己更新。</strong></p>
</blockquote>
<hr>
<h2 id="四、真正的-Boss：Windows-构建环境">四、真正的 Boss：Windows 构建环境</h2><p>代码层修完，本以为胜利在望。然后 Windows 教我做人。</p>
<p>技术栈：RN 0.82.1 &#x2F; AGP 8.12.0 &#x2F; Gradle 8.13 &#x2F; Kotlin 2.1.20 &#x2F; compileSdk 36 &#x2F; NDK 27。下面按踩坑时间线记录。</p>
<h3 id="1-Defender-实时扫描锁死-Gradle-原生库">1. Defender 实时扫描锁死 Gradle 原生库</h3><p>Gradle 8.13 一启动就报：</p>
<figure class="highlight plaintext"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br></pre></td><td class="code"><pre><span class="line">Could not initialize native services.</span><br><span class="line">Failed to load native library &#x27;native-platform.dll&#x27; ...</span><br><span class="line">java.io.FileNotFoundException: ...native-platform.dll.lock (拒绝访问。)</span><br></pre></td></tr></table></figure>

<p><code>dll</code> 本身能加载，普通文件读写删都正常，唯独 Gradle 用 <code>RandomAccessFile</code> 给 <code>.lock</code> 加锁时被<strong>微软 Defender 实时防护</strong>在创建瞬间排他锁住**。</p>
<p>解法：把这三个目录加进 Defender 排除项（或临时关掉实时保护）：</p>
<ul>
<li><code>C:\Users\\.gradle</code>（含各种缓存目录）</li>
<li>独立的 Android 构建目录（如 <code>E:\android-build</code>）</li>
<li><strong>项目目录本身</strong>（这点最容易被漏，C++ 编译产物 <code>android/app/.cxx</code> 就在项目里，不排它一样卡死）</li>
</ul>
<h3 id="2-260-字符路径上限-过时的-ninja">2. 260 字符路径上限 + 过时的 ninja</h3><p>C++ 编译一开，ninja 报 <code>Filename longer than 260 characters</code>。</p>
<p>注册表开了 <code>LongPathsEnabled=1</code> 并重启后，ninja 1.10.2（SDK 自带）还是翻车——它太老，不认长路径。</p>
<p>解法：把 SDK 里的 <code>cmake/3.22.1/bin/ninja.exe</code> 备份后，替换成 <strong>ninja 1.12.1</strong>。</p>
<h3 id="3-clang-死锁假死">3. clang 死锁假死</h3><p><code>clang++</code> 进程 CPU 占用 0%，看起来在编译，实际死等。根因还是 Defender 在扫 <code>.cxx</code> 产物 + CMake 高并行度下的文件锁竞争。</p>
<p>解法：降并行度 <code>CMAKE_BUILD_PARALLEL_LEVEL=4</code>，并把项目目录彻底排除出实时扫描。</p>
<h3 id="4-残留进程-陈旧-daemon-锁">4. 残留进程 &#x2F; 陈旧 daemon 锁</h3><p>最阴的是：中途强杀后台构建，会留下一堆陈旧锁文件（<code>.o.d</code>、<code>registry.bin.lock</code>、<code>native-platform.dll.lock</code>）和还活着、占着文件句柄的 <code>java</code>&#x2F;<code>clang</code>&#x2F;<code>ninja</code> 进程。下次构建一上来就被这些僵尸锁挡住，报错和「第一次」一模一样，极其迷惑。</p>
<p>解法：跑之前先</p>
<figure class="highlight powershell"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br></pre></td><td class="code"><pre><span class="line"><span class="comment"># 杀残留进程</span></span><br><span class="line">taskkill /F /IM java.exe /IM clang*.exe /IM ninja.exe</span><br><span class="line"><span class="comment"># 清陈旧构建态</span></span><br><span class="line"><span class="built_in">Remove-Item</span> <span class="literal">-Recurse</span> <span class="literal">-Force</span> android/app/.cxx</span><br><span class="line"><span class="comment"># 清 Gradle daemon 与 native 锁</span></span><br><span class="line"><span class="built_in">Remove-Item</span> <span class="literal">-Recurse</span> <span class="literal">-Force</span> <span class="variable">$env:GRADLE_USER_HOME</span>/daemons</span><br></pre></td></tr></table></figure>

<p><strong>而且同一时刻只跑一条构建，别让多个后台任务抢同一批锁文件。</strong></p>
<hr>
<h2 id="五、来之不易的进展">五、来之不易的进展</h2><p>排除项加全、长路径和 ninja 升好、并行度降下来之后，链路是这样跑通的：</p>
<ul>
<li>✅ 配置所有 autolinked 原生库</li>
<li>✅ 下载 3.4GB 依赖</li>
<li>✅ Java &#x2F; Kotlin 全量编译</li>
<li>✅ JS Bundle（Metro）打包</li>
<li>✅ reanimated &#x2F; vision-camera &#x2F; worklets 等 C++ 原生模块陆续编译通过</li>
<li>⏳ 仅差 <code>llama.cpp</code> native 收尾 + 最终 APK 打包</li>
</ul>
<p>也就是说，<strong>代码和构建配置层面已经全部打通</strong>，离出包只差最后一段原生编译。只是这段最慢、也最容易因为前面说的「残留锁」被打断——我最后几次就是卡在 Gradle 又被一个陈旧 <code>native-platform.dll.lock</code> 拦下来，APK 暂时还没产出。</p>
<hr>
<h2 id="六、如果你也要在-Windows-上搞-RN-本地-LLM，照这个清单来">六、如果你也要在 Windows 上搞 RN + 本地 LLM，照这个清单来</h2><ol>
<li><strong>先确认 SDK 组件齐全</strong>：<code>sdkmanager</code> 装 <code>platforms;android-36</code>、<code>build-tools;36.0.0</code>、<code>cmake</code>。</li>
<li><strong>NDK 别写死</strong>：<code>local.properties</code> 里删 <code>ndk.dir</code>，让 AGP 按模块 <code>ndkVersion</code> 自适应，避免 <code>CXX1104</code>。</li>
<li><strong>缺 <code>.env</code> &#x2F; Firebase 就绕</strong>：复制 <code>.env.example</code>；没有 <code>google-services.json</code> 就注释掉 <code>google-services</code> 插件和 firebase 依赖。</li>
<li><strong>改了 llama.cpp 模型源码就必须源码编</strong>：<code>-PrnllamaBuildFromSource=true -PrnllamaVariants=rnllama</code>。</li>
<li><strong>ABI 收敛到 <code>arm64-v8a</code></strong>：手机基本都是这个，能省掉一大半编译量。</li>
<li><strong>Defender 排除三项</strong>：<code>.gradle</code> 缓存、Android 构建目录、<strong>项目目录本身</strong>。</li>
<li><strong>开 <code>LongPathsEnabled</code>，并把 ninja 升到 ≥ 1.11</strong>（SDK 自带 1.10.2 不够）。</li>
<li><strong><code>CMAKE_BUILD_PARALLEL_LEVEL=4</code></strong>，别让 clang 把文件锁打满。</li>
<li><strong>跑前清残留</strong>：杀 <code>java/clang/ninja</code> 进程 + 删 <code>.cxx</code> + 清 Gradle daemon；<strong>同一时刻只跑一条构建</strong>。</li>
</ol>

<h2 id="七、写在最后">七、写在最后</h2><p>回头看，这场「下午茶项目」前后耗了十来天，真正和 AI &#x2F; 模型相关的改动其实就一个补丁文件；剩下 90% 的精力，都耗在 Windows 构建环境的各种隐性锁、路径限制和杀软冲突上。</p>
<p>端侧大模型的门槛，从来不只是模型本身，还有这条把模型送进设备的、脆弱又磨人的工具链。</p>
<p>APK 我还在收尾——等最后那段原生编译跑完，下一篇可以聊聊真机上的首 token 延迟和续航实测。</p>
