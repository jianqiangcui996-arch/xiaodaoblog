<p>核心认知修正：<strong>Tailscale 解决的是”我控制设备去连服务器”，Cloudflare Tunnel 解决的是”任意客户端访问一个服务”</strong>。这两件事在 NAT 后的虚拟机上完全不等价。</p>
<h2 id="一、先把地基修好：VM-连-IP-都拿不到">一、先把地基修好：VM 连 IP 都拿不到</h2><p>在谈对外服务之前，先处理了一个更基础的问题——虚拟机重启后彻底失联。</p>
<h3 id="1-1-症状与我的第一次误判">1.1 症状与我的第一次误判</h3><p>Windows 宿主机重启后，SSH 连不上 VM。VM 控制台里 <code>ip a</code> 显示：</p>
<figure class="highlight plaintext"><table><tr><td class="gutter"><pre><span class="line">1</span><br></pre></td><td class="code"><pre><span class="line">2: eth0: &lt;BROADCAST,MULTICAST&gt; mtu 1500 state DOWN   ← 注意没有 UP 标志</span><br></pre></td></tr></table></figure>

<p>第一反应是”Hyper-V 的 Default Switch 网段随重启漂移，静态地址失效了”。<br>这个判断<strong>对了一半</strong>——网段确实每次重启都换（我机器上历史出现过 5 个不同网段），<br>但它不是主因，因为那个静态地址压根就没生效过。</p>
<h3 id="1-2-真凶：netplan-的-MAC-匹配失效">1.2 真凶：netplan 的 MAC 匹配失效</h3><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br></pre></td><td class="code"><pre><span class="line">networkctl</span><br><span class="line"><span class="comment">#   IDX LINK  TYPE  OPERATIONAL SETUP</span></span><br><span class="line"><span class="comment">#   2   eth0  ether routable    unmanaged    ← 关键：unmanaged</span></span><br></pre></td></tr></table></figure>

<p><code>unmanaged</code> 意味着<strong>没有任何网络管理器在管这块网卡</strong>。翻配置：</p>
<figure class="highlight yaml"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br></pre></td><td class="code"><pre><span class="line"><span class="comment"># /etc/netplan/00-installer-config.yaml</span></span><br><span class="line"><span class="attr">ethernets:</span></span><br><span class="line">  <span class="attr">eth0:</span></span><br><span class="line">    <span class="attr">match:</span></span><br><span class="line">      <span class="attr">macaddress:</span> <span class="number">00</span><span class="string">:15:5d:02:10:04</span>     <span class="comment"># 配置里匹配这个 MAC</span></span><br></pre></td></tr></table></figure>

<p>而实际网卡 MAC 是 <code>00:15:5d:02:10:05</code>。连安装器写的原始备份也是 <code>:04</code><br>——说明这块虚拟网卡在装完系统后被重建过（迁移&#x2F;重建 VM 时 Hyper-V 重新分配了动态 MAC）。<br><strong>MAC 匹配不上 → 整份配置对这块网卡无效 → 既没静态地址也没 DHCP 兜底</strong>。</p>
<blockquote>
<p>教训：<code>ip a</code> 看不到地址时，先看 <code>networkctl</code> 的 SETUP 列而不是急着改地址。<br><code>unmanaged</code> &#x3D; 配置没匹配上；<code>configuring</code> &#x2F; <code>failed</code> 才是配置本身有问题。</p>
</blockquote>

<h3 id="1-4-网络定型：双网卡分工">1.4 网络定型：双网卡分工</h3><p>最终架构，也是这次所有事的基础：</p>
<figure class="highlight plaintext"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br></pre></td><td class="code"><pre><span class="line">宿主机 Windows</span><br><span class="line">├─ vEthernet (Default Switch)  172.x.0.1/20      ← Hyper-V 自管的 NAT，每次开机自动重建</span><br><span class="line">│    └─ VM eth0：DHCP，只要地址、不要默认路由（兜底 SSH 入口）</span><br><span class="line">└─ vEthernet (VMIntNet)        192.168.100.1/24  ← 自建内部交换机（永久网段）</span><br><span class="line">     └─ VM eth1：静态 192.168.x.10，只负责入站，不配默认路由</span><br><span class="line"></span><br><span class="line">出网：VM → eth0 → Default Switch 的 NAT → 互联网</span><br><span class="line">入站：宿主 → eth1 的静态地址（永远不变，不受宿主重启影响）</span><br></pre></td></tr></table></figure>

<p>对应 netplan 关键片段：</p>
<figure class="highlight yaml"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br></pre></td><td class="code"><pre><span class="line"><span class="attr">eth0:</span></span><br><span class="line">  <span class="attr">match:</span> &#123; <span class="attr">macaddress:</span> <span class="number">00</span><span class="string">:15:5d:02:10:05</span> &#125;   <span class="comment"># 一定用实际 MAC</span></span><br><span class="line">  <span class="attr">dhcp4:</span> <span class="literal">true</span></span><br><span class="line">  <span class="attr">dhcp4-overrides:</span> &#123; <span class="attr">use-routes:</span> <span class="literal">false</span>, <span class="attr">use-dns:</span> <span class="literal">false</span> &#125;   <span class="comment"># 只要地址，不抢路由</span></span><br><span class="line"><span class="attr">eth1:</span></span><br><span class="line">  <span class="attr">match:</span> &#123; <span class="attr">macaddress:</span> <span class="number">00</span><span class="string">:15:5d:02:10:07</span> &#125;</span><br><span class="line">  <span class="attr">addresses:</span> [ <span class="number">192.168</span><span class="number">.100</span><span class="number">.10</span><span class="string">/24</span> ]</span><br><span class="line">  <span class="comment"># 故意不写 routes: —— 原因见下面的坑</span></span><br></pre></td></tr></table></figure>

<p><strong>这里踩过一个惨痛的坑</strong>：我一开始给 eth1 配了 <code>routes: [to: default, via: 192.168.100.1]</code>，<br>出网走自建内部交换机的 <code>New-NetNat</code>。结果宿主重启一次就全网瘫痪——<br><strong><code>New-NetNat</code> 建的 NAT 对象不会在宿主重启后存活</strong><br>（portproxy、宿主侧静态 IP、防火墙规则全都持久，唯独 NAT 不持久）。<br>而 eth0 被我设成 <code>use-routes: false</code>，于是 VM 一条默认路由都没有，<br>DNS 最先死，Tailscale 表现为 “logged out”，很容易误判成 Tailscale 故障。</p>
<blockquote>
<p>正确做法：<strong>出网交给 Hyper-V 自己托管的 Default Switch NAT</strong>（它每次开机自动重建），<br>内部交换机那条静态网卡只当”永久入站入口”用，不配默认路由。</p>
</blockquote>
<h2 id="二、两个值得单独记的坑">二、两个值得单独记的坑</h2><h3 id="2-1-磁盘”只剩-19G”是假象">2.1 磁盘”只剩 19G”是假象</h3><p><code>df -h /</code> 显示根分区 19G、剩 8.5G，正准备停机扩 VHDX，结果 <code>pvs</code> 一看出问题了：</p>
<figure class="highlight plaintext"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br></pre></td><td class="code"><pre><span class="line">PV         VG        PSize    PFree</span><br><span class="line">/dev/sda3  ubuntu-vg &lt;36.95g  18.47g      ← 18.47G 白躺在 VG 里</span><br></pre></td></tr></table></figure>

<p>Ubuntu 安装器<strong>默认只把 VG 的 64% 切给根 LV</strong>。所以：</p>
<figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br></pre></td><td class="code"><pre><span class="line"><span class="built_in">sudo</span> lvextend -l +100%FREE /dev/ubuntu-vg/ubuntu-lv</span><br><span class="line"><span class="built_in">sudo</span> resize2fs /dev/ubuntu-vg/ubuntu-lv      <span class="comment"># ext4 支持在线扩，不停机不提权不动 VHDX</span></span><br></pre></td></tr></table></figure>

<p>19G → 37G，30 秒搞定。真要扩 VHDX 是另一回事<br>（停机 → <code>Resize-VHD</code> → <code>growpart</code> → <code>pvresize</code> → <code>lvextend</code> → <code>resize2fs</code>）。</p>
<blockquote>
<p>教训：Linux 虚拟机磁盘不够，<strong>先 <code>pvs</code> 看 PFree</strong>，别一上来就动虚拟磁盘。</p>
</blockquote>
<h3 id="2-2-VS-Code-反复要密码，而命令行-SSH-免密正常">2.2 VS Code 反复要密码，而命令行 SSH 免密正常</h3><p>这个现象非常迷惑：命令行 <code>ssh devbox</code> 秒进，VS Code Remote-SSH 每次弹密码框。<br>两个原因叠加。</p>
<p><strong>原因一，陈旧 <code>.pub</code> 造成的假指纹。</strong><br><code>ssh-keygen -l -f id_ed25519</code> 报了个指纹，我拿它去装公钥，服务端拒绝。<br>真相是 <strong><code>ssh-keygen -l</code> 读私钥时会去拿同名的 <code>.pub</code> 文件</strong>，<br>而那个 <code>.pub</code> 是上一把密钥的残留（私钥重新生成过，<code>.pub</code> 没更新）。<br>客户端拿 <code>.pub</code> 里的 blob 去 offer、却用不匹配的私钥签名 → 必然被拒。</p>
<figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br></pre></td><td class="code"><pre><span class="line">ssh-keygen -yf id_ed25519 &gt; id_ed25519.pub     <span class="comment"># 从私钥反导出真正的公钥</span></span><br></pre></td></tr></table></figure>

<p><strong>原因二，私钥文件的 NTFS ACL 太松。</strong><br>Windows 自带的 OpenSSH（VS Code 用的就是它）会检查私钥权限，<br>发现 <code>BUILTIN\Users</code> 和 <code>Everyone</code> 可读，就<strong>静默跳过密钥</strong>退化成密码认证。<br>而 git-bash 里那个 OpenSSH 10.x 不做这个检查——所以”我能连、VS Code 不能连”。</p>
<figure class="highlight powershell"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br></pre></td><td class="code"><pre><span class="line">icacls <span class="variable">$key</span> /inheritance:<span class="built_in">r</span> /remove <span class="string">&quot;BUILTIN\Users&quot;</span> <span class="string">&quot;Everyone&quot;</span></span><br><span class="line">icacls <span class="variable">$key</span> /grant:<span class="built_in">r</span> <span class="string">&quot;<span class="variable">$</span>&#123;env:USERNAME&#125;:F&quot;</span> /grant <span class="string">&quot;NT AUTHORITY\SYSTEM:F&quot;</span></span><br></pre></td></tr></table></figure>

<blockquote>
<p>补充坑：PowerShell 里 <code>&quot;$env:USERNAME:F&quot;</code> 会被解析成作用域变量而变空，<br>必须写成 <code>&quot;${env:USERNAME}:F&quot;</code>。</p>
</blockquote>
<h2 id="三、主线：让手机从任何网络打开-1Panel">三、主线：让手机从任何网络打开 1Panel</h2><p>地基修好，进入正题。1Panel 在 VM 里监听 <code>0.0.0.0:8443</code>，本机 curl 200 正常。</p>
<h3 id="3-1-尝试一：Tailscale-直连-VM-——-架构上不可行">3.1 尝试一：Tailscale 直连 VM —— 架构上不可行</h3><p>手机和 VM 都在同一个 tailnet，VM 有 <code>100.x.x.x</code>，理论上手机直接访问<br><code>http://100.x.x.x:8443</code> 就行。结果超时。</p>
<p><strong>这里有个极容易骗过自己的现象</strong>：在手机上 <code>tailscale ping &lt;VM的100.x&gt;</code> 是有 pong 的！<br>但抓包一看，VM 侧<strong>一个 SYN 都没收到</strong>。</p>
<p>原因有两层：</p>
<ol>
<li><strong><code>tailscale ping</code> 是 disco 协议层应答</strong>，由 <code>tailscaled</code> 进程直接回，<br><strong>根本不经过内核网络栈、不产生 TCP 连接</strong>。ping 通 ≠ 业务数据能传。</li>
<li><strong>方向不对称</strong>。VM 藏在 Hyper-V 的 Default Switch NAT 后面：<ul>
<li>VM <strong>主动</strong>去 ping 对端 → 包能出去，NAT 记住回程映射 → 有 pong ✅</li>
<li>对端<strong>主动</strong>连入 VM 的 <code>100.x</code> → 需要宿主上有对应的入站映射，Hyper-V 不会给 → 丢弃 ❌</li>
<li>本该退化成 DERP 中继兜底，但<strong>国内访问 Tailscale 官方 DERP 基本连不上</strong> ❌</li>
</ul>
</li>
</ol>
<p>更离谱的是：<strong>同一个 WiFi 下的手机和宿主机，tailscale 也打洞失败</strong>，<br>只能绕旧金山中继，RTT 500ms+（而 NAT 后面的 VM 反而能直连手机）。</p>
<figure class="highlight plaintext"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br></pre></td><td class="code"><pre><span class="line">pong from tailscale-termux (100.98.x.x) via DERP(sfo) in 507ms</span><br><span class="line">direct connection not established</span><br></pre></td></tr></table></figure>

<blockquote>
<p>结论：这种拓扑下，别拿 Tailscale 做”别人来访问我的服务”。</p>
</blockquote>
<h3 id="3-2-尝试二：用-portproxy-桥宿主的-Tailscale-IP-——-不接管-wintun">3.2 尝试二：用 portproxy 桥宿主的 Tailscale IP —— 不接管 wintun</h3><p>思路很漂亮：宿主机自己是正常的 tailscale 节点，而且有直达 VM 内网的路由，<br>那就让宿主替 VM 收连接：</p>
<figure class="highlight powershell"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br></pre></td><td class="code"><pre><span class="line">netsh interface portproxy add v4tov4 listenaddress=&lt;宿主<span class="number">100</span>.x&gt; listenport=<span class="number">8443</span> `</span><br><span class="line">     connectaddress=<span class="number">192.168</span>.<span class="number">100.10</span> connectport=<span class="number">8443</span></span><br></pre></td></tr></table></figure>

<p><strong>而且我差点被自己的测试骗了</strong>：在宿主机上 <code>curl http://&lt;宿主100.x&gt;:8443</code> 返回 200，<br>我当场宣布”桥通了”。错——<strong>本机访问自己的 IP 走回环，完全不经过入站防火墙和真实收包路径</strong>。<br>换手机测，照样超时。</p>
<p>最终定位：<code>netsh portproxy</code>（iphlpsvc）不接管 Tailscale 那张 wintun 网卡上的入站连接。<br>这条路放弃。</p>
<blockquote>
<p>铁律：<strong>验证”外部能否连入”，必须换一台机器测。</strong><br>本机自测 200 只能证明监听和回源是好的。</p>
</blockquote>
<h3 id="3-3-尝试三：公网域名-路由器端口转发-——-两个假象叠加">3.3 尝试三：公网域名 + 路由器端口转发 —— 两个假象叠加</h3><p>域名在 Cloudflare 做**灰云（DNS only）**直指家宽公网 IP，路由器加端口转发。<br>逻辑上完全成立，实测超时。这里叠了两个假象。</p>
<p><strong>假象一：NAT 回环（hairpin）。</strong><br>在<strong>家里 WiFi</strong> 上访问自己的公网 IP，绝大多数家用路由器不支持回环，必然超时。<br>判别方法：宿主机自己 <code>curl http://&lt;公网IP&gt;:8443</code> 超时、但 <code>curl http://192.168.x.7:8443</code> 是 200。<br>所以<strong>测公网链路必须关 WiFi 用移动数据测</strong>，否则你会把”回环不支持”误判成”公网不通”。</p>
<p><strong>假象二：端口转发规则填错。</strong> 后来发现规则实际是：</p>
<figure class="highlight plaintext"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br></pre></td><td class="code"><pre><span class="line">局域网主机:      192.168.x.7:8443    ← 错，这个字段只能填纯 IP</span><br><span class="line">局域网主机端口:  45432               ← 错，服务实际在 8443</span><br></pre></td></tr></table></figure>

<p>正确写法是”局域网主机”只填 IP、”局域网主机端口”填<strong>服务真实端口</strong>、<br>“广域网端口”才填对外端口。填错之后转发到了本机一个没人监听的端口，当然超时。</p>
<blockquote>
<p>也就是说：我一度得出的”运营商封端口”结论，其实根本没被真正验证过。<br>排查到这里我做了个决定——不再跟端口转发斗智斗勇，直接上 Cloudflare Tunnel。</p>
</blockquote>

<h2 id="五、修正上一篇的结论">五、修正上一篇的结论</h2><p>上一篇我说 Tailscale 是”个人远程开发的默认最优解”。现在补一个边界：</p>
<table>
<thead>
<tr>
<th>需求</th>
<th>该用什么</th>
<th>原因</th>
</tr>
</thead>
<tbody><tr>
<td><strong>我用自己的设备连进服务器</strong>（SSH、开发）</td>
<td><strong>Tailscale</strong></td>
<td>服务器主动出站打洞即可，方向天然正确</td>
</tr>
<tr>

<tr>
<td>同一局域网内的日常访问</td>

<td>最快，零依赖</td>

<p>一句话：<strong>Tailscale 是”拉”，Cloudflare Tunnel 是”挂”</strong>。<br>NAT 后的机器做”拉”很擅长，做”被访问”就只能靠一根主动出站的隧道。</p>
<p>两者不冲突，我的最终形态是并存：SSH 走 Tailscale + 内网静态地址，Web 面板走 Cloudflare Tunnel。</p>

<h2 id="八、一句话总结">八、一句话总结</h2><blockquote>
<p><strong>NAT 后面的虚拟机，”被访问”和”去访问”是两件难度完全不同的事。</strong><br>Tailscale 让后者变得极其舒服，前者则要靠”服务主动出站到 Cloudflare”这类反向隧道。<br>我把三条看似合理的路都走了一遍才承认这一点——<br>而最贵的不是配置，是那些”看起来成功了”的假信号：<br>有 pong 的 <code>tailscale ping</code>、返回 200 的本机自测、<br>以及”所有设备都超时”其实只是路由器不支持 NAT 回环。</p>
</blockquote>
